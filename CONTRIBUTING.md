# Contributing

Nooks is a household todo app you run yourself. It is one Go binary serving an API and a
React app from the same process, with everything in one SQLite file.

This page is how to get it running and what is expected of a change. The reasoning
behind those expectations is in four other files, and they are worth reading before a
first change rather than after a first review:

| File | What it settles |
| --- | --- |
| [`STANDARDS.md`](STANDARDS.md) | How code is written here, and why each rule is a rule |
| [`CONTEXT.md`](CONTEXT.md) | What every word means — 26 terms, each with what *not* to call it |
| [`DESIGN.md`](DESIGN.md) | Every colour, size and state. UI work follows it rather than improvising |
| [`AGENTS.md`](AGENTS.md) | The working rules and the code map, in short form |

## Getting it running

You need Go 1.27.1, Node 24.21.0 and pnpm 12.3.4. The Node version is in `.nvmrc`; buf
is a workspace dependency, so there is nothing to install globally.

```bash
pnpm install
go run ./cmd/nooks --addr :8081
```

In a second terminal:

```bash
cd apps/web && pnpm dev
```

The dev server proxies the API to `:8081`, so the browser talks to one origin and
cookies behave as they do in production. Open the address it prints. The first person to
arrive creates the owner account and names the instance.

## Before you push

```bash
./scripts/ci.sh
```

Everything CI runs, in the same order: the Go build, vet, tests and formatting; proto
lint, format and a breaking-change check against `main`; the web typecheck, lint and
tests; the app build; and what a first visit costs.

It takes a few minutes. It is faster than finding out from CI, and much faster than
finding out from somebody using it.

## What a change is expected to do

**Read the surrounding code first.** Prefer the local pattern over a new abstraction.
A file that does something unlike its neighbours costs more than the duplication it
saved.

**Explain the why, not the what.** The code says what it does. A comment earns its place
by saying why it is this way — what was tried, what broke, what the alternative would
cost. There are comments throughout doing exactly that, and they are the reason nobody
has to rediscover the same thing twice.

**Keep the diff scoped.** No repo-wide cleanup, no dependency churn, no reformatting.
The repository is not Prettier-formatted; running a formatter over it is a large diff
that hides a small change.

**Do not edit generated files.** Change the `.proto` and run `pnpm generate`.
`apps/web/src/components/ui/` is generated by shadcn — wrap it in `components/ds/`
rather than editing it, so `shadcn add` can still overwrite the original.

**Tests are part of the change.** Not for their own sake: a test earns its place by
being able to fail. Several guards here exist because something shipped broken once, and
each was checked by breaking it deliberately and watching the guard catch it. Do that
with yours.

## Conventions worth knowing before you start

- **One verb for creating things: Add.** Never New, Create, Issue, or Generate.
- **Types are named**, never written inline in a signature.
- **`useEffect` is a last resort.** `useSyncExternalStore`, render-time computation,
  event handlers and TanStack Query cover nearly everything. There is exactly one in the
  tree, inside a generated shadcn component, and none in code we wrote.
- **Dates go through `apps/web/src/lib/dates.ts`**, numbers through `lib/format.ts`.
  Nothing reaches for `date-fns` or `Intl` directly.
- **Every string a Member reads lives in `src/i18n/locales/en.json`.** A new language is
  a JSON file and one entry in `i18n/locales.ts`.
- **Schema changes need a migration for every driver**, and an updated `LATEST.sql` for
  each.

## Commits

[Conventional Commits](https://www.conventionalcommits.org), no body or a very short
one:

```
feat(web): say when the instance cannot be reached
fix(api): refuse a text change that would overwrite another
docs(website): explain the api before listing it
```

The subject says what changed for somebody using Nooks, not which files moved.

## Ask first

Some changes are cheaper to discuss than to review:

- A heavy dependency.
- Anything touching authentication, access tokens or what they reach.
- The Docker image or the release workflow.
- A change to `DESIGN.md` itself, as opposed to implementing it.

Open an issue. A short description of the problem is enough to start.
